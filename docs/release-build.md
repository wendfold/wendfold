# Release build notes

## Goals of this layout

This monorepo keeps source separate from release artifacts.

- source lives in the extension directories and `pkg_wendfold/`
- generated installer ZIPs go to `build/dist/`
- temporary staging output goes to `build/staging/`

This avoids treating GitHub snapshot archives as public installers.

## Build outputs

`python3 build/build_release.py` writes these files to `build/dist/`:

- `pkg_wendfold_vX.Y.Z.zip`: the suite package, the only file that is published
- `com_wendfold_vX.Y.Z.zip`, `plg_user_wendfold_vX.Y.Z.zip`, `plg_task_wendfold_vX.Y.Z.zip`, `plg_privacy_wendfold_vX.Y.Z.zip`: internal build outputs. The package carries them under `constituents/`. They are never published on their own.
- `SHA256SUMS.txt`: internal checksums for all five ZIPs, used by CI and the release workflow

## What gets published

Releases are package-only:

- **Package source, GitHub Releases:** `https://github.com/wendfold/wendfold/releases/download/vX.Y.Z/pkg_wendfold_vX.Y.Z.zip` and `https://github.com/wendfold/wendfold/releases/download/vX.Y.Z/SHA256SUMS-vX.Y.Z.txt`. The update feed's `<downloadurl>` points here. The release workflow builds these, together with the update feed, as the site-upload bundle (see `RELEASING.md`). The maintainer uploads it after the maintainer's approval.
- **GitHub Release assets:** the release workflow attaches exactly four assets to the draft release: `pkg_wendfold_vX.Y.Z.zip`, `SHA256SUMS-vX.Y.Z.txt`, `pkg_wendfold.xml` (with `<sha256>` filled in), and `wendfold-site-bundle-vX.Y.Z.zip`. A guard step fails the job if anything else, such as a child ZIP, is staged.

The draft release notes are generated by the release workflow from the version's section in `CHANGELOG.md` with `scripts/release/generate-changelog.py --notes-out` (bullets tagged `<!-- internal -->` are left out). There is no hand-written release body; see `RELEASING.md`, sections 2b and 4.

Operational publishing steps are provided in:

- `RELEASING.md`
- `docs/release-checklist.md`

## Package behavior

The suite package is the only public installer.

- it installs the component first
- it installs the user plugin second
- it installs the task plugin third
- it blocks individual uninstall of child extensions when they were installed as part of the package

The package installer script enables the three companion plugins on a fresh package install.
When the package is installed on top of an existing site that already had one or both plugins, the script preserves the existing enabled or disabled state for those plugins.

## Build exclusions

`build/build_release.py` leaves these source-only files out of the ZIPs:

- `BACKLOG.md` in `com_wendfold/` (component ZIP)
- `updates/` and `.gitignore` (every child ZIP)
- `.gitignore` (package ZIP); `constituents/` in the package is rebuilt from the freshly built child ZIPs on every run

The suite update feed lives in `updates/` at the repository root. It is published separately and is not packed into the extension ZIPs.

README and LICENSE files remain in the child extension ZIPs.

## Release publishing notes

When publishing a release, on the GitHub Release or the wendfold.com download page:

- offer `pkg_wendfold_vX.Y.Z.zip` as the only installer, with `SHA256SUMS-vX.Y.Z.txt`
- do not publish the child ZIPs or the internal `SHA256SUMS.txt`
- do not point users to GitHub's automatic source archives as installers

## Live update note

The suite registers one update server, on `pkg_wendfold`, pointing at `https://wendfold.com/updates/pkg_wendfold.xml`.
Child manifests do not declare update servers.
Each `<update>` entry's `<downloadurl>` is `https://github.com/wendfold/wendfold/releases/download/vX.Y.Z/pkg_wendfold_vX.Y.Z.zip`.
